# SHUSHA Shopify bridge

This merchant extension is GPL-3.0-only and uses documented EverShop exports. It does not replace EverShop's upstream catalog/order modules. The bridge is disabled by default; migrations, production-copy rehearsal, merchant OAuth approval and staged acceptance precede enablement.

## Foundation: authentication and catalog drafts

Server configuration is read from `SHOPIFY_BRIDGE_ENABLED`, `SHOPIFY_SHOP`, `SHOPIFY_APP_URL`, `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`, `SHOPIFY_TOKEN_ENCRYPTION_KEY`, and optional `SHOPIFY_SCOPES`. The encryption key is exactly 32 random bytes encoded as canonical base64. No values belong in Git, browser bundles, logs, or API responses. `SHOPIFY_BRIDGE_WRITES_ENABLED=true` is additionally required by the import CLI. Admin GraphQL is pinned to `2026-10`; changing it requires review and regression coverage.

OAuth starts from an authenticated EverShop administrator. The signed state binds that merchant identity, the fixed shop and a ten-minute expiry; the callback atomically consumes its nonce. Callback parameters use Shopify's HMAC validation; webhooks validate the original bounded raw body before parsing, then validate the fixed shop, allowed topic and delivery ID. The authorization code requests expiring offline credentials. Access/refresh tokens are AES-256-GCM encrypted together with store-bound associated data. Authorization and refresh share the repository's shop lock; refresh rotates and persists both credentials before returning the access token. Transient failures preserve the old encrypted pair, while rejected/expired authorization requires merchant action.

The repository must offer durable session advisory locks and autocommit writes before remote calls. Token repositories expose `withLock`, `get`, `save` and `remove`. Catalog repositories expose `withLock`, product/media mapping reads/writes and operation journal reads/writes. Nested product → media → token locks use the same database connection; original remote intent survives process failure. GraphQL query retries are bounded and respect throttle cost/Retry-After. Generic mutation transport/server failures return an unknown outcome, without automatic replay. Mutation-specific idempotent retries need the original persisted request and key; there is no invented HTTP idempotency header.

`scripts/shopify/export-catalog.mjs` uses a dedicated repeatable-read **read-only** database transaction and the existing publication/price locks. Its private snapshot selects completed, publicly enabled publication plans, validates current store-map/SKU/UUID, actual colour/size, original-image gallery and explicit visual review, then verifies local image size, signature and SHA-256. It reads no customer or historical-order tables. Missing review, changed files, unmapped variants and stale mapping ownership fail closed. Remaining request capacity is recorded without resetting it, including negative debt. Private output is confined to the Shopify subdirectory of `PRIVATE_DATA_DIR`.

```sh
node scripts/shopify/export-catalog.mjs
node scripts/shopify/import-catalog.mjs
# Only after installation, USD currency and private rehearsal acceptance:
node scripts/shopify/import-catalog.mjs --apply
```

Import is a local dry-run by default. Applied import checks Shopify's native currency is USD, stages hash-verified originals without forwarding an Admin token to storage, creates named image files with duplicate rejection and waits for READY before attachment. Product handles are `l####`; the private ownership metafield binds the original product UUID. One source style becomes one **DRAFT** with only its actual published colour/size pairs. SKU, native variant/inventory GIDs and image mappings are privately retained. Product image ordering and all variant-image associations are read back. Unknown creation outcomes are journaled and reconciled through the owned handle/filename; absence does not authorize another blind creation.

Phase-three `--apply --activate-inventory` additionally requires `SHOPIFY_INVENTORY_ACTIVATION_ENABLED=true`, an approved `SHOPIFY_LOCATION_ID`, and inventory scopes. Activation only accepts owned mapped drafts. It persists the original UUID idempotency key, activates a missing native inventory level at Shopify's zero default without sending quantities, and checks native item/location ownership. Existing levels are never overwritten. Unknown retries use the same request within the provider window; unresolved near-expiry requests pause for merchant review. Shared-capacity opening remains a separate transaction and outbox process.

The existing minute worker can call `createCatalogFollower(runtime)`. It reads current completed publication plans and original-image manifests, imports newly published source styles as drafts, and optionally activates their reviewed inventory location. READY unpublished source materials never enter this snapshot. Automatic channel publication requires all of `SHOPIFY_CATALOG_PUBLICATION_ENABLED`, `SHOPIFY_SHARED_CAPACITY_ENABLED`, and `SHOPIFY_PAYMENT_OPERATIONS_ENABLED`, plus approved location/publication IDs. Every SKU must have a reconciled opening balance, no pending inventory writes, exact native/central/debt projection and matching remote quantity before ACTIVE/channel publication. Those writes are journaled and read back; unknown outcomes are paused until their original result is visible.

Native Shopify prices are the exact shared retail calculation: source Resale USD × 1.1, rounded up to the smallest `.99`. EverShop native prices remain source USD. Repeated mapped imports use `productVariantsBulkUpdate` with only `id` and `price`; they refuse structural replacement. No import writes inventory quantities, historical orders, receiving details or customer data. Catalog changes beyond prices need a separately reviewed structural operation. Publication, shared-capacity opening and accepting Shopify orders remain gated by their later batches.

Foundation tests use only synthetic credentials, styles, local generated fixtures and injected transports. They cover HMAC/state replay, encrypted store binding, concurrent refresh, bounded retries, lost mutation responses, USD/ownership gates, original-image integrity, draft repeat-run recovery, price boundaries and price-only updates. A passing local test does not establish Shopify installation, API permissions, live import, payments or production acceptance.

Primary API contracts: [standalone OAuth](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens/authorization-code-grant), [token refresh](https://shopify.dev/docs/apps/build/authentication-authorization/access-tokens), [productSet list semantics](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/productSet), [staged upload](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/stagedUploadsCreate), [fileCreate](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/fileCreate), [variant media association](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/productVariantAppendMedia), and [price bulk update](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/productVariantsBulkUpdate).

Compatibility: source pricing is imported from the merchant retail-pricing extension, while database reads follow EverShop 2.2.1's public catalog schema and existing merchant publication ledger. Upgrade rehearsals must verify these field names and the native editor-to-safe-HTML conversion. `sanitize-html` is explicitly pinned to the dependency version already supplied by this fork.
