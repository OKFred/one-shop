# Shopify manual quotes, Wise access and native fulfillment

The bridge keeps native Shopify money and status authoritative. A Wise receiving URL displays instructions; it does not prove incoming funds, add a card gateway, transfer money or accept payment automatically. Shipping is quoted manually after availability is checked. Historical EverShop orders and their original payment URLs remain in EverShop; they are not recreated as Shopify orders. Cross-platform actual receipt references use one global unique registry.

## API and account compatibility

Admin GraphQL is pinned to `2026-10`. The independently versioned customer-account UI is pinned to the officially published `2026-07` API and `@shopify/ui-extensions@2026.7.0`, with Preact 11 and native `s-*` components. An unregistered, empty extension template lives in `shopify/extensions/wise-payment`; the authorized app's Shopify CLI generates its UID. No legacy React extension runtime or hypothetical 2026-10 UI SDK is used. The block must be added in the checkout and accounts editor. Its static order-menu target places the entry on the owned order list. Legacy customer accounts need a separate reviewed implementation; this extension targets Shopify's new customer accounts.

The app needs `read_orders`, `write_orders`, `write_order_edits`, `read_customers`, `read_merchant_managed_fulfillment_orders` and `write_merchant_managed_fulfillment_orders` in addition to catalog scopes. Account data/ownership requires Shopify protected customer data access and any approval Shopify requires for that app/distribution. Session tokens omit the customer subject when access or full sign-in is missing; the server fails closed. The extension declares `network_access` and needs its required approval. Native staff permissions include order editing, `mark_orders_as_paid` and `fulfill_and_ship_orders`. Orders older than Shopify's default 60-day API window need approved `read_all_orders`; otherwise show a support fallback and never bypass ownership checks.

The store must be USD for both native and presentment money in this flow. Foreign-currency markets, card/online gateway orders, authorizations, captures, third-party fulfillment locations, partial native payments and complex native shipment cases require separate review. Do not silently convert their order amounts. Configure actual manual gateway names as an explicit allowlist and merchant-managed location GIDs as an explicit allowlist. Confirm the store's manual checkout payment method before opening orders.

## Private phase 4 enablement

Keep all switches off in the empty [runtime template](../shopify/extensions/wise-payment/runtime.example.env) until the corresponding rehearsal and authenticated acceptance pass. The bridge still needs its foundation shop, HTTPS app origin, app credentials, encrypted-token key and reviewed OAuth scopes. Adding scopes in an environment file does not grant them: install/reauthorize the merchant-approved app and verify the actual granted permissions.

| Operation | Required private runtime switches |
| --- | --- |
| Quote, actual receipt, native paid registration, shipment | `SHOPIFY_BRIDGE_ENABLED`, `SHOPIFY_BRIDGE_WRITES_ENABLED`, `SHOPIFY_PAYMENT_OPERATIONS_ENABLED` |
| Unpaid order cancellation and its reconciliation | The three payment switches above, plus `SHOPIFY_SHARED_CAPACITY_ENABLED` and `SHOPIFY_ORDER_OPERATIONS_ENABLED` |
| Reviewed prepared content apply | `SHOPIFY_BRIDGE_ENABLED`, `SHOPIFY_BRIDGE_WRITES_ENABLED`, `SHOPIFY_CONTENT_SYNC_ENABLED`, plus the saved plan's explicit review hash |

The administrator receives separate `paymentWritesEnabled` and `orderWritesEnabled` booleans. The component's `writesEnabled` and `orderWritesEnabled` props both default to false; enabling payment controls does not enable cancellation or its reconciliation. Every confirmation starts unchecked. A canonical cancellation displays the original operation key, keeps payment/shipment controls paused, and offers only `reconcile-cancel` for a pending/unknown original outcome. Successful or pending cancellation refreshes the parent order view. Changing the selected order requires a matching fresh native inspection before any action can run.

Before payment access is enabled, set `SHOPIFY_PAYMENT_ACCESS_SECRET` to a dedicated random secret distinct from the app secret, set `SHOPIFY_MANUAL_GATEWAYS` to the exact reviewed native manual gateway names, and set `SHOPIFY_FULFILLMENT_LOCATION_IDS` to the approved active merchant location GIDs. Both lists are private JSON arrays. `SHUSHA_WISE_RECEIVING_CONFIG` points to the existing private receiving file; USD fields must be explicitly approved with `allowUsd:true`. The public template contains no receiving fields or bank values.

OAuth acceptance must verify `write_order_edits` for native shipping editing separately from `write_orders` for paid registration and cancellation. Account ownership requires `read_customers` and protected customer data approval; native order reads require order access. Shipment requires the approved merchant-managed fulfillment scopes and the native user's `fulfill_and_ship_orders` permission. Cancel restock checks need location read access (`read_locations` or the existing `read_inventory` scope). Native UI network capability approval, the customer-account block/menu installation and actual USD manual checkout settings remain independent provider steps. Nothing in the template, installed code or a passing synthetic test proves these permissions are granted.

## Private repository and request contracts

`createPaymentService({shop,client,repository,receivingConfig,allowedManualGateways,writesEnabled,now})` and `createFulfillmentService({shop,client,repository,allowedLocationIds,writesEnabled,now})` require the authenticated Admin client and a durable repository. Writes are disabled by default. Runtime `SHOPIFY_PAYMENT_OPERATIONS_ENABLED=true` additionally requires global `SHOPIFY_BRIDGE_WRITES_ENABLED=true` for mutations. `SHOPIFY_MANUAL_GATEWAYS` and `SHOPIFY_FULFILLMENT_LOCATION_IDS` are reviewed JSON lists in the private environment. The repository implements `withOrderLock(orderGid,callback)`, `getQuote(orderGid)`, `saveQuote(orderGid,value)`, `getOperation(key)`, `saveOperation(key,value)`, `getReceipt(reference)`, `claimReceipt(receipt)` and `listReceipts(orderKey)`. The lock must serialize every worker/merchant process for the same shop/order. Intent, invalidation and native stages must commit durably before each external mutation; do not roll back the entire callback as a single database transaction after a network failure. Production additionally implements `assertOrderOperable(orderGid)` for canonical cancel intents: all payment/shipment operations call it within their order lock. Customer credential issuance/redemption also fails for unresolved or completed canonical cancellations, including when the native API read is stale.

Receipt records are `{reference,platform:'shopify',orderKey:shop+':'+orderGid,currency:'USD',amount:'12.34',quoteRevision,createdAt}`. Normalize reference to uppercase with collapsed spaces, and retain a single global primary key without platform/shop prefixes. `claimReceipt` atomically claims the global row and persists the receipt ledger, returning `{created:boolean}`. Identical duplicates read back the original receipt; any different order, platform, amount, currency or quote revision fails. Native bank-transfer receipts must seed and use the same registry before Shopify receipt actions become enabled. No partial funds are auto-refunded, reassigned or marked paid.

Confirmed quotes privately store revision, paymentVersion, unchanged native money, confirmed shipping, remaining/received amounts, actual reference and a frozen receiving configuration. The configuration shape is `{verified:true,bankDetails:[{label,value}],wiseBusinessOpenLink:null}` with an optional verified `https://wise.com/pay/business/<handle>` receiving URL. Adapt existing validated USD receiving fields into this shape at runtime; no placeholders become a live receiving configuration. Receiving details, quotes, operation requests, receipts and diagnostics remain private. Changing runtime bank details does not silently change an existing confirmed quote's destination.

`confirmShippingQuote({orderId,operationKey,expectedQuoteRevision,shippingTitle,shippingAmount,merchantAvailabilityConfirmed:true})` accepts exact decimal USD strings, including fractional and zero shipping. It durably inactivates the previous quote before `orderEditBegin`, replaces native shipping lines or updates an added line, then commits with `notifyCustomer:false`. Native merchandise, discounts, shipping, calculated tax, total, outstanding USD and unchanged pre-commit money are read back before the new quote activates. CalculatedOrder's actual `taxLines.priceSet` are summed; no nonexistent `totalTaxSet` field is assumed. Missing, rejected, changed or unknown native results leave payment inactive. Unknown mutations are never automatically replayed, even with a new operation key.

`recordReceipt({orderId,receiptReference,amount,currency:'USD',quoteRevision,receivedConfirmed:true})` requires independent verification of actual incoming funds. Partial receipt aggregation is central only, updates the remaining amount and invalidates previous access credentials. Full central receipts produce `received`, hide the payment entry and require a separate merchant action. `markPaid({orderId,operationKey,quoteRevision,receivedConfirmed:true,markPaidConfirmed:true})` verifies the global ledger, current native money and manual gateway before calling `orderMarkAsPaid`; it activates `paid` only after native PAID/zero-outstanding readback. `reconcilePaid(operationKey)` can read back an unresolved native result and finalize the original journal without replaying a mutation.

Shopify's `orderMarkAsPaid` can capture an existing authorized payment. The service therefore rejects capturable orders, authorized status, every card/online payment detail, authorization/capture transaction and non-allowlisted gateway before that mutation. Shopify does not expose a conditional compare-and-set version on this mutation. A concurrent external native writer can still change an order between query and mutation. Operate these orders through the bridge under its durable lock, keep this store's payment methods manual during the initial release, and investigate native gateway changes before enabling paid registration. This guard is not a claim that all provider races are eliminated.

`fulfill({orderId,operationKey,actualShippedConfirmed:true,trackingInfo:{company,number,url},lines:[{fulfillmentOrderId,fulfillmentOrderLineItemId,quantity}]})` requires actual shipment, verified central/native paid status and explicit shipped quantities at one allowlisted merchant location. It never omits line selections to imply "fulfill all". It persists the selected native IDs, prior fulfillment IDs and actual tracking before `fulfillmentCreate({notifyCustomer:false,...})`. The actual native SUCCESS fulfillment, matching quantities and tracking are read back before completion. Unknown outcomes retain a pending shipment marker; `reconcile(operationKey)` only reads and matches the original shipment, excludes prior fulfillments and never resends it. Explicit confirmation controls records, not a courier booking API or automatic customer message.

## Customer access and route requirements

The native customer extension calls `shopify.sessionToken.get()` immediately before each request. The officially published 2026-07 SDK defines `get():Promise<string>`; its signed session payload identifies `dest` as the shop hostname, `aud` as the app client ID and `sub` as a Customer GID. A missing subject, wrong shop/app, invalid signature or expired token is rejected before native order ownership is read. The customer POST contract is `{orderId}` with a bearer header; a successful response is exactly `{data:{paymentUrl,expiresAt,quoteRevision}}`. The extension checks this envelope, short expiry and same-origin signed destination. Denied/unavailable entries expose no payment control or private backend error. The local HTTP contract regression exercises the actual parser, issuer, helper and signed payment page against synthetic read-only native order data.

`createCustomerPaymentAccess({shop,client,repository,appSecret,clientId,accessSecret,appUrl,allowedManualGateways,now})` provides `issue(sessionToken,orderId)` and `redeem(accessToken)`. Use a dedicated random server-side access secret of at least 32 characters distinct from the Shopify app secret. Runtime names are shown without values in `shopify/extensions/wise-payment/runtime.example.env`; the backend origin setting is empty until its verified app route is deployed.

The entry route is `POST /api/shopify/payment-access`, accepting `Authorization: Bearer <Shopify session JWT>` and JSON `{orderId}`. Verify HS256 signature with the app secret, exact audience/client ID, destination shop, expiry/not-before/issued-at, and a signed `gid://shopify/Customer/...` subject. Anonymous and pre-authenticated sessions fail. Query the live Admin API to verify the actual shop and customer ownership, and validate the active native amount and quote. Only then issue `{paymentUrl,expiresAt,quoteRevision}` with a maximum five-minute access credential bound to shop, order, customer, quote revision and paymentVersion. The credential contains no customer contact or bank data. The authenticated page rechecks live ownership, native amount, quote/version, cancellation and expiry on every redemption. A cancelled, changed, inactive, received or paid quote cannot disclose payment instructions.

Credential issuance and redemption hold the same repository order lock as merchant cancellation, quotes, receipts and shipment operations through the guard, native read and final snapshot construction. A central cancel/quote/payment change cannot intervene between authorization and the private receiving snapshot. Credential expiry is rechecked after waiting for that lock and after provider reads; an expired waiting request returns no entry or receiving fields.

Return no-store responses with `Referrer-Policy: no-referrer`; disable analytics, third-party assets and request/query-string logging on the payment page. Never include the access credential in telemetry, screenshots, referrers or customer messages. Treat this short credential URL as sensitive bearer access while it is valid. Display only escaped text fields and the already validated official Wise URL after redemption. The existing local Wise SVG can be served from the merchant app; Shopify's sandbox UI does not accept arbitrary custom SVG/CSS and instead uses the full-width native primary button. The customer-account UI keeps the URL in memory and refreshes it before expiry.

Shopify customer-account extensions run in a sandboxed Web Worker with an unrecognizable/null origin. On this bearer-only entry endpoint and its credential-free OPTIONS preflight, Shopify's [official capability documentation](https://shopify.dev/docs/apps/build/customer-accounts/capabilities#required-cors-headers) requires `Access-Control-Allow-Origin: *`, allowing POST/OPTIONS, Authorization and Content-Type. Do not enable `Access-Control-Allow-Credentials`; UI requests explicitly omit cookies. Scope these headers to the entry endpoint, not the private merchant API. CORS is not authorization: every POST still verifies the signed customer subject and native ownership. Never accept a client-supplied customer ID, shop, price, bank field or return URL. Invalid/unowned/pending/received states should return sanitized 401/403/404/409 responses; provider failures should render a support fallback. Apply body limits and rate limits without logging tokens or private bodies. Merchant quote/receipt/paid/fulfillment endpoints must require native admin authentication and permission, never the customer bearer.

## Acceptance boundary

Synthetic tests exercise signed token rejection, live ownership, changed/expired versions, zero/fractional shipping, durable intent-before-write, tax mismatch, cross-platform duplicate receipts, partial/full funds, card refusal, unknown-result reconciliation and shipment quantity/location checks. The native UI can be locally bundled against the pinned official SDK. These are code and synthetic acceptance only. Real app installation, protected-data/network permissions, native account desktop/mobile keyboard preview, live manual gateway settings, exact provider API behavior, actual receiving configuration and real order flow require authenticated provider acceptance before opening Shopify orders. No real incoming payment, paid registration, shipment or notification is performed by these tests.
