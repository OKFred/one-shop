# Shared request capacity and EverShop 2.2.1 compatibility

EverShop and Shopify accept requests against one signed central capacity. Capacity is a request limit, not a guarantee of supplier stock. Supplier price synchronization must not replenish it. All bridge tables, mappings, inbox payloads and reports belong to the private operational database and volumes.

## Transaction integration

EverShop 2.2.1 deducts stock through `TRIGGER_AFTER_INSERT_ORDER_ITEM`, installed by checkout migration `Version-1.0.2.js`. The trigger updates `product_inventory.qty` in the order transaction. Before it runs, the public `hookBeforeSaveOrderItems` at priority 0 reads native `cart.getItems()` and each item's `product_sku`/`qty`. It locks mapped native rows before central rows, then rejects unopened, frozen or insufficient signed capacity. Concurrent EverShop checkouts therefore cannot consume the same remaining central capacity. The extension registers the public `hookAfterSaveOrderItems` at priority 900 with the callback arguments `(result, cart, orderId, connection)`. It records the already-completed deduction, central ledger and outbox on that exact connection. It does not deduct native stock twice and must not use a new pool connection or an after-commit event for this work. The query builder sets `connection.INTRANSACTION`; the bridge rejects an unowned transaction connection.

Cancellation uses `hookBeforeUpdatePaymentStatusToCancel` to lock and re-read the native order before any native status update or restock. An already canceled order is rejected. Every mapped managed line needs its recorded release basis. `hookAfterReStockAfterCancel` writes the release ledger and outbox before native commit. Hook-after callbacks receive the native result before the original arguments. The bridge consumes the public OMS service exports added by this fork; the upstream cancellation implementation and its stock arithmetic are retained. Export compatibility must be checked at every upstream upgrade.

Incoming Shopify stock deltas lock native product inventory before the central row, matching the native checkout trigger's lock order. A transaction failure rolls back the native mirror and its acknowledgement together. Shopify orders are stored through their own adapter and are never inserted into EverShop's native `order` table.

## Opening and additional published styles

Opening is an explicit operation, never a scheduled stock reset. Take a backup and establish a native write barrier for the initial cutover. Validate the current catalog/map, the selected Shopify location, variant IDs and managed native inventory. Shopify variants remain drafts and cannot accept orders. Activate the mapped inventory item at the reviewed location with the separate persisted activation operation, then independently verify available quantity zero.

`openCapacity(connection, {skus})` locks those native product rows, copies their actual remaining signed quantity and records pending historical line quantities as the permitted legacy cancellation basis. It creates one opening delta intent. A repeated opening does not rewrite capacity or create another intent. The opening outbox refuses any unexplained nonzero Shopify quantity. Only after its opening intent and subsequent deltas have drained, with matching native/central/debt-aware readback, may phase 4 publish Shopify products and accept orders.

For a newly published style, the same sequence runs while Shopify remains a draft. A lock of that style's native inventory captures orders completed before opening in the legacy basis. It does not restore consumed capacity to 999 or require historical customer/order import into Shopify.

After actual Shopify publication, the optional `SHOPIFY_CONTENT_SYNC_ENABLED` follower maintains the three native category collections using their existing category UUID identities and private content mappings. It reads all complete reviewed native publications, verifies the mapped Shopify ownership and actual publication, and refreshes bounded full membership in original newest-first publication order. Drafts and READY-only material never enter those collections. A durable pending digest permits readback recovery after a crash; a completed unchanged digest skips content writes. The content synchronizer and initial import share `content-sync:<shop>` locking. This job changes collections and their canonical category redirects, not pages, navigation, themes or assets. Collections retain their merchant-controlled publication state.

## Delta delivery, debt and recovery

Each order-line business effect has a unique ledger key independent of webhook delivery IDs. The ledger and outbox are transactional. One session advisory lock serializes the outbox processor; an unresolved earlier intent blocks later intents for its aggregate. The existing native cron calls the minute worker and the 15-minute reconciliation job. It does not start another cron or event-manager daemon.

Shopify writes use `inventoryAdjustQuantities`, an explicit `changeFromQuantity` CAS value and a persisted UUID through `@idempotent`. Both the exact variables and their key are durable before the first request. An unknown result reuses both. A `CHANGE_FROM_QUANTITY_STALE` response proves the attempted CAS did not write and permits a fresh read and new attempt. Generic failures are not proof. Unresolved attempts freeze five minutes before the documented 24-hour retention limit; the stock transport performs one bounded attempt per worker call. Parameter mismatch freezes the SKU. Retrying beyond the retention period is a merchant investigation, not a regenerated key.

EverShop and the central balance retain negative capacity. Shopify represents its effective balance as native available quantity minus private debt. Mirrored deltas consume or repay debt before producing positive available quantity. A Shopify-native restock also queues a CAS normalization with central delta zero, so its returned units repay existing debt. No negative balance is truncated and then treated as an inventory reset.

Relevant API contracts: [incremental inventory adjustment](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/inventoryAdjustQuantities), [CAS input](https://shopify.dev/docs/api/admin-graphql/2026-10/input-objects/InventoryChangeInput), [idempotency and retention](https://shopify.dev/docs/apps/build/apis/graphql-admin/implementing-idempotency).

## Orders and reconciliation

Verified webhook deliveries are persisted before processing. The worker hydrates the current native order with bounded pagination and rejects a snapshot that changes between pages. Duplicate/late deliveries cannot repeat cumulative consumption or verified release. A canceled status or refunded amount does not prove stock was returned: `RefundLineItem.restocked`/restock type or a completed private native-restock operation provides the release basis. Ambiguous cancellation, removed lines without restock evidence, unmapped SKUs and incomplete pagination need investigation. Customer data is not copied into public fixtures or reports.

The 15-minute job fills missing recent native order facts and checks native balance plus unapplied deltas against the signed central balance. It also observes Shopify effective balance; a stable unexplained remote difference needs a second observation after 15 minutes, with no pending delivery or unknown remote write, before freezing. Reconciliation never assigns an absolute stock count. Its cursor advances only after a complete bounded scan. Without approved `read_all_orders`, older than 60-day orders remain a clearly identified native-admin task.

[Refund line inventory evidence](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/RefundLineItem) is distinct from financial receipt confirmation. No bridge worker verifies real incoming funds, pays, refunds or messages a customer.

## Focused acceptance

`tests/operations.inventory.test.mjs` uses synthetic data and an isolated local PostgreSQL database when `SHUSHA_BRIDGE_TEST_DATABASE_URL` is supplied. It refuses nonlocal hosts and databases whose name does not end in `_test`. It installs the actual EverShop stock trigger and actual additive bridge migrations. Its SQL tests cover opening from remaining capacity, legacy cancellation basis, native checkout guards and concurrent capacity consumption, native transaction rollback on outbox failure, concurrent duplicate cancellation, duplicate/out-of-order Shopify effects, both channels' debt repayment, lost responses, crash after provider success, confirmed CAS nonwrite, expiry freezing and reconciliation without a reset. `tests/operations.hooks.test.mjs` executes the saved bootstrap body and actual native registration functions/Hookable utility, checking public exports, before/after argument positions, original connection identity, priorities, disabled gates and the two registrations with the existing native cron. Provider responses are synthetic: these tests do not establish live Shopify write acceptance.

An upstream upgrade additionally needs the restored-production rehearsal and live private readback specified in the project instructions. Keep the old image, newest orders and payment records protected before rollback; never run EverShop v1 against the v2 database.
